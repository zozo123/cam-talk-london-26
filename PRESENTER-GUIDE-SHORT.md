### 04. In parallel computing, the costly work is the work done twice.

### 05. A cache skips work a previous run already did.

*0:45; starts 3:10*

Here is how a cache works. Hash a build step's inputs, the source, the flags and the toolchain, into a key. If the key is stored, that is a hit: reuse the stored output. On a miss, run the step in a sandbox and store its output, so the next run hits. The sandbox hides undeclared files, so the step cannot read what the key omits. This is the Incredibuild lesson: never build the same thing twice. Remember that hash; it comes back. Here is what it buys.

**Q&A detail**

The diagram is the generic content-addressed action cache used by ccache, Bazel remote caching and Incredibuild: the key is a hash of the declared inputs (sources, flags, toolchain); a hit reuses the stored output; a miss runs the step and stores its output under the key. Sandboxing (hermetic execution) hides undeclared files, so a step cannot silently depend on inputs the key omits; time, randomness, network and nondeterministic tools still need declaring or excluding, so the key covers every input only when the step is hermetic. Bazel's local sandbox hides undeclared workspace files, but system directories typically stay visible read-only; hermetic toolchains or a pinned remote-execution image close that gap. The hash proves identity of inputs, not correctness of outputs. This is the same content-identity thread that later binds a receipt to checked bytes and names what the controller publishes. We do not claim that a fork is faster than a good build cache.

### 07. A fork extends caching from files to a reached execution state.

*0:45; starts 4:35*

A fork goes further: it restores the state after many steps, such as installed dependencies or a warmed process. Think of a film: fixed scenes, and rewinding replays the same plot. An experiment saves a reached state, keyed by its digest like a cache entry, and tries two next actions, each in its own private sandbox. A check keeps one outcome and discards the other, and we continue from there. Step three makes that sharing safe.

**Q&A detail**

Cache versus fork: both are reuse, and both need a key. A cache returns one step's stored output, keyed by its inputs; a fork restores a captured execution state, the state after many steps, and lets several private continuations diverge from it. Proposed: the parent is immutable and named by its digest; a child is that digest plus its private delta. Changing an input that reached the parent needs a new parent, as a cache miss would. The islo snapshots we measured are named snapshots; we do not claim they are content-addressed today. Which state a fork must capture depends on the next action: files and cached inputs, or supported memory and runtime state. Installed dependencies are file state; a reproduced failure in a running application is a hypothetical future live-state workload, not an observed property of our factory runs; a warmed process requires a process or VM checkpoint whose memory semantics must be checked. The comparison priced later is restoring saved state versus rebuilding with a warm cache; we do not claim that a fork is faster than a good build cache. Adaptive planning, search, operating-system process fork and feedback control have long histories; the claim is an organizing research direction, not historical priority or new computational expressive power. Forkability and autonomy are separable: a runtime may fork without an agent, and an agent may operate serially without forks. The film analogy refers to private executable continuations from saved computer state. It does not rewind completed model or tool requests, incurred costs, published data or other external-world effects, and restoring a snapshot does not establish a child's current authority.

### 08. A sandbox lets children share one state safely.

*0:50; starts 5:20*

Here is the sandbox. In our design, three children share one saved state, read-only and named by its digest. Each child writes only to its own private layer, so siblings cannot overwrite each other. Undeclared inputs stay hidden, which keeps the cache key complete. Effects, like a network request, do cross the boundary; no restore rewinds them, so we propose recording them. This is the Twistlock lesson: a sandbox bounds behavior. It is a policy; a VM with its own kernel, or a container sharing one, is one way to build it. Here are the three steps as code.

**Q&A detail**

Proposed model: the shared parent state is immutable (read-only) and named by its digest; each child is that digest plus its own private write layer, so siblings cannot overwrite each other. The boundary has three jobs. Private writes keep alternatives independent until a check accepts one. Hiding undeclared inputs keeps the cache key complete (the step cannot read what the key omits). Effects that cross the boundary, such as a model request, a network call or a push, are not rewound by any restore; the proposal is to record them once (effect journal, idempotency keys), and a restored child must not hold publication authority. Runtime layers are different dimensions rather than interchangeable isolation levels: a conventional VM or microVM runs a guest kernel behind a virtualization boundary (Firecracker uses KVM and a minimal device model); a Linux container shares the host kernel, with namespaces for separate views and cgroups for resource limits; a sandbox is a policy over what execution may access and do, and may be built on a VM, a container, syscall mediation (gVisor) or another mechanism. cgroups alone do not define file access, network policy or syscall permissions; capabilities, seccomp and LSMs are additional mechanisms. Docker Sandboxes, accessed with the sbx CLI, is a microVM-based product with a private Docker daemon and host proxy, not a synonym for an ordinary Docker container. Our factory runs (SELFHOST-2 and SELFHOST-3) ran serially in Docker Sandboxes, not islo, and nothing forked. A sandbox bounds local effects; it does not undo remote ones. No universal startup-time or safety ranking is asserted.

### 10. Caches, forks and sandboxes are old; coupling them to evidence and acceptance is new.

*0:50; starts 6:55*

A cache keeps run outputs, as in ccache, Bazel's remote cache or Incredibuild. A fork keeps reached states: SnowFlock cloned Xen machines in two thousand nine, and Xen came from this lab. A sandbox keeps writes private, as containers, gVisor and microVMs do. What is new is what sharing requires: count shared evidence once, and publish checked bytes once. I do not claim a fork speedup, since our agent runs were serial, or that our snapshots keep live memory. So what does sharing work cost us? Three rules.

**Q&A detail**

The table names established mechanisms; no claim of invention, comprehensive priority or measured parallel speedup is made. Forking states to search is also old: KLEE (Cadar, Dunbar and Engler, OSDI 2008) and S2E (Chipounov, Kuznetsov and Candea, ASPLOS 2011) fork execution states; the AFL forkserver forks an initialized target per input; Potemkin (Vrable et al., SOSP 2005) flash-clones VMs. The claim is the evidence and acceptance contract around reuse, not search by forking. The contribution claim is the integrated execution, evidence and acceptance contract: reuse a state only when it beats rebuilding it, count shared observations once, and publish the exact checked bytes once from a controller. What each mechanism must guarantee: a cache key covers every input (only for hermetic steps: time, randomness, network and undeclared files must be declared or excluded); a fork's capture keeps what the next step needs; a sandbox hides undeclared inputs and keeps writes private. Fork semantics are backend-specific: worktrees preserve source views, process checkpoints (CRIU, gVisor save/restore) and VM snapshots (Xen, SnowFlock, Firecracker) preserve only their declared state surfaces, and filesystem snapshots do not establish memory capture. SnowFlock: Lagar-Cavilla et al., Rapid Virtual Machine Cloning for Cloud Computing, EuroSys 2009, built on Xen; Xen came from the Cambridge Computer Laboratory (Barham et al., SOSP 2003). Bazel here means its remote cache. A sandbox bounds local effects; it does not undo remote effects, and a restored child must not hold publication authority. Not claimed: our factory runs (SELFHOST-2 and SELFHOST-3, 27 September 2026) ran serially in Docker Sandboxes, not islo, and nothing forked, so no fork speedup is measured; we do not claim that a fork is faster than a good build cache. ### 11. Sharing work creates three rules.

*0:50; starts 7:45*

Sharing work creates three obligations, and they organize this talk. Compute once: reuse or rebuild? Reuse a state only when that beats rebuilding it, even from a warm cache. The answer is a cost rule. Count once: what must a trial return? Parallel trials share inputs and errors, so a shared observation counts once. That needs an evidence contract. Publish once: who publishes what? One controller publishes the exact bytes that passed the check, through an acceptance gate. You will leave with all three. Five examples first, then the rules in order.

**Q&A detail**

This slide restates the canonical three system responsibilities. Runtime starts private continuations and supplies the state the next step reads, priced against a warm alternative such as a build cache. An evaluator or recorder outside child-controlled state binds executed checks to exact artifact digests and records which observations trials share. Acceptance selects or composes candidates after the appropriate check; the controller retains publication authority. Once is the goal of each obligation, not an exactly-once delivery guarantee: compute once means do not repeat preparation when a saved state supplies what the next step reads; count once means a shared observation contributes once to a combined result; publish once means one controller publishes one checked artifact and rejects stale results (the epoch fence is proposed). The contribution claim is the integrated execution, evidence and acceptance contract; forking, testing, review and provenance are established techniques, and no claim of invention or measured parallel speedup is made.

### 12. Reuse makes fuzzing fast; only checks turn crashes into findings.

*1:00; starts 8:35*

First example: software security. A fuzzer runs a program on many changed inputs, hunting for crashes. AFL-plus-plus initializes the target once, then reuses one child process across many inputs. Its documentation reports typical speedups of ten to twenty times. It wins by not forking for every input, as long as state resets correctly. That is rule one, compute once. But speed only produces leads, and leads need checks. In a separate study, Berkeley's CyberGym, an AI agent wrote and ran inputs against 431 projects and produced fifty-six crashes. The researchers reproduced them and removed duplicates: twenty-two distinct new vulnerabilities. That is rule two, count once. Second example: AI research.

**Q&A detail**

Two separate sources: AFL++ documentation supplies the speed figure; CyberGym is a separate agent study that does not claim AFL++ or persistent-mode reuse. AFL++: the documented typical 10–20x gain is for persistent mode, which avoids a process fork for every input; it must not be attributed solely to the deferred forkserver. The forkserver defers cloning until initialization is complete; a persistent child then runs the harness repeatedly, resetting mutable state between inputs. About 1,000 iterations before restarting is a recommended starting point, not a fixed setting. Gains depend on the target and reset correctness. A newly executed input is not automatically an independent observation, and a crash is not automatically an exploitable vulnerability. CyberGym latest-code campaign (report checked 4 October 2026): OpenHands with GPT-5 on 431 latest OSS-Fuzz projects and 1,748 runnable executables produced 56 crashes; the authors reproduced, deduplicated and investigated them, confirming 22 distinct previously unknown vulnerabilities. Projects, targets, crashes and validated bugs are different units; the funnel is not a disjoint 22/56 success probability, and exploitability or patch status is not implied. This is separate from CyberGym's historical 1,507-vulnerability benchmark across 188 projects. The separate GPT-4.1 campaign's counts overlap and cannot be added. Neither result measures sandbox forking or our own security campaign.

### 13. Autoresearch kept 23 of 126 attempts against a fixed evaluator.

*1:00; starts 9:35*

Here, Karpathy's autoresearch starts every attempt from the incumbent commit, and the commit hash names that exact state. The evaluator stays fixed. The agent edits the training script, trains for five minutes, and reads validation bits per byte, where lower is better. Then it keeps or reverts. One reported session made 126 attempts, one at a time, and kept twenty-three. The score fell 2.8 percent. Starting from the incumbent is compute once; only the fixed evaluator promotes a change, which is publish once. AlphaEvolve extends this loop to a population of programs; one scheduling heuristic it found recovered 0.7 percent of Google's compute, on average. Third example: software engineering.

**Q&A detail**

Autoresearch: one reported session, not a controlled average effect or a fork experiment. 126 attempts: 23 kept, 102 discarded, 1 crash. The score decline is (0.997900-0.969686)/0.997900=2.827%; lower validation bits per byte is better. The protocol holds data preparation, tokenizer and evaluation fixed and permits editing train.py. Five minutes is wall-clock training time; startup and compilation are outside that budget, and crashes can end early. Sequential Git keep/revert is the actual mechanism; forked parallel continuations are a possible extension, not what produced this result. Repeated adaptive selection on one validation set warrants a separate held-out check before claiming generalization. AlphaEvolve: DeepMind reports that the discovered Borg scheduling heuristic recovered an average 0.7% of Google's worldwide compute resources, in production for over a year at announcement. A separate kernel result (23% kernel speedup, 1% lower Gemini training time) is a different workload and endpoint; the gains are not additive. Gemini Flash and Pro propose edits; automated evaluators check validity and performance; evolutionary selection keeps useful programs. The gains belong to the discovered algorithms, not to a sandbox fork or our implementation.

### 15. Our CRISPR screen narrowed 19,050 genes to about 100 candidates.

**Q&A detail**

### 30. Five questions remain open; the preregistered tests have not started.

*1:05; starts 25:40*

Five questions remain open. Three have preregistered tests; none has started. Compute once. First, and first to run: does the snapshot we restore keep live memory? VM checkpoints can; we have not shown that ours does. A value held only in RAM must survive into three restored children. Until then, I say restore fan-out, not memory fork. Second, does restoring beat a warm cache at three, six and twelve sandboxes? Count once. Third, do restored siblings fail a race test together more than restores of other snapshots? That measures the shared environment, not agents' judgments. Fourth, a design question: when should the reducer refuse a precision claim? Publish once. Fifth, does the epoch fence hold across restores? Our TLA+ model is not yet model-checked. Now, what this talk contributes.

**Q&A detail**

No result is claimed until the protocol runs. No decision rule has changed since prereg-v1 (later amendments de13c1d, prereg-v2 and prereg-v3 updated slide references and corrected a Phase B standard-error note); any change must be a dated amendment before collection. Gate 0 comes first, because H1's reached-state restore is only a disk restore if memory is not kept: a live process holds a random 128-bit nonce only in RAM; take a named snapshot, restore three children and check that the process is alive with the same nonce. It is a necessary probe, not a full fidelity proof; if the nonce does not survive, every report says restore fan-out (many restores of one named snapshot). VM and process checkpoints (Xen save/restore, SnowFlock, Firecracker, CRIU) capture memory by design; the open question is whether the named-snapshot restore path we measured keeps it. Measured restore fan-out: a named 141 MB islo snapshot, restore–run–capture round trips, 255 of 256 succeeded at concurrency 12, p50 6.87 s, p95 9.04 s, client-measured, teardown excluded (arXiv:2607.09689v4, Table 2). These are API round trips, not mechanism latency or a provider ranking. H1: compare reached-state restore with a warm cached template at N = 3, 6 and 12 concurrent cells, 20 repetitions per arm and N, interleaved in random order; batch makespan is primary; gain is median cached minus median restore makespan, with 10,000 within-arm bootstrap resamples. It supports H1 if the 95% lower confidence bound exceeds 10 s at every N and rejects if the Bonferroni 98.3% upper bound is below 10 s at any N; other outcomes are inconclusive. Cold start is a reference only. Capture accounting and resource cost are not makespan. H2: 12 snapshot families of 3 restored siblings; strangers are restores from other families started in the same slot, so both arms restore and only shared ancestry differs. The statistic is the intraclass correlation of race-test outcomes; support needs a one-sided permutation p below 0.05 and an excess above 0.05, and rejection (90% upper bound below 0.05) rules out a shared-ancestry excess of 0.05 or more, not all dependence. H2 measures environmental race-test co-failure, not dependence between agent judgments. Reused families and repeated rounds make pair differences dependent; an analysis amendment is proposed and must precede collection. Reducer: the built reducer rejects repeated declared evidence IDs and carries lineage; abstention when dependence is unknown and a controller-derived precision are proposed. Distinct IDs do not prove independence. Question 5: the epoch fence and promotion rule exist as a TLA+ design model with no TLC run or trace check recorded, so neither has been model-checked; restores and controller crashes are the cases to check. Beyond the five, the companion note (Speculative Sandboxes, 13 Oct 2026) asks when a fork should exist at all: it writes the probability that any branch is accepted with the chain rule over earlier failures, which does not assume independent siblings; its Python controller is a finite-world mock, not a forked islo integration. Acceptance and correctness are different variables.

### 31. Contributions: three rules for doing work once.

*1:00; starts 26:45*

My contributions, on the same map we started with. Compute once: a cost rule. Restore saved state only when the setup it avoids exceeds the overhead it adds, priced against a warm cache. Count once: an evidence contract. The reducer I built rejects duplicate observation IDs; receipts kept outside the child and weights for shared errors are proposed. Publish once: an acceptance gate. The controller holds the key and publishes exact bytes; that check is built. A test for every promise and the epoch fence are proposed. One hash threads all three: it keys the cache, binds the receipt, and names the published bytes. It proves identity, not correctness. Compute once. Count once. Publish once. Your questions, please.
