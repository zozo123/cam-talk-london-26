\sources{Organizing analogy and proposed execution model. A restore does not rewind requests already sent.}
\qadetail{Cache versus fork: both are reuse, and both need a key. A cache returns one step's stored output, keyed by its inputs; a fork restores a captured execution state, the state after many steps, and lets several private continuations diverge from it. Proposed: the parent is immutable and named by its digest; a child is that digest plus its private delta. Changing an input that reached the parent needs a new parent, as a cache miss would. The islo snapshots we measured are named snapshots; we do not claim they are content-addressed today. Which state a fork must capture depends on the next action: files and cached inputs, or supported memory and runtime state. Installed dependencies are file state; a reproduced failure in a running application is a hypothetical future live-state workload, not an observed property of our factory runs; a warmed process requires a process or VM checkpoint whose memory semantics must be checked. The comparison priced later is restoring saved state versus rebuilding with a warm cache; we do not claim that a fork is faster than a good build cache. Adaptive planning, search, operating-system process fork and feedback control have long histories; the claim is an organizing research direction, not historical priority or new computational expressive power. Forkability and autonomy are separable: a runtime may fork without an agent, and an agent may operate serially without forks. The film analogy refers to private executable continuations from saved computer state. It does not rewind completed model or tool requests, incurred costs, published data or other external-world effects, and restoring a snapshot does not establish a child's current authority.}
\note{[0:45] A fork goes further. It restores the state after many steps, like installed dependencies or a warmed process. Think of a film. Its scenes are fixed, and rewinding replays the same plot. An experiment is different. It saves a reached state, keyed by its hash, like a cache entry. It tries two next actions, each in its own private sandbox. A check keeps one outcome and discards the other. Then we continue from there. Step three makes that sharing safe.}
