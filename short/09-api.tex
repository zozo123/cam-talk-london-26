\begin{frame}[fragile,t]{\ev{\tagP}\surf{IN CODE}The forkable API prepares once and runs alternatives in private children.}
\vspace{.05cm}
\begin{columns}[T,onlytextwidth]
\column{.45\textwidth}
{\fontsize{14}{17}\selectfont\bfseries Python loop\par}
\begin{lstlisting}[style=slidepython,basicstyle=\ttfamily\fontsize{12}{14.6}\selectfont]
out = []
for edit in edits:
    env = prepare()
    env.apply(edit)
    out.append(test(env))
best = select(out)
\end{lstlisting}
\column{.53\textwidth}
{\fontsize{14}{17}\selectfont\bfseries\color{Teal}Forkable API\par}
\begin{lstlisting}[style=slidepython,basicstyle=\ttfamily\fontsize{12}{14.6}\selectfont]
parent = checkpoint(prepare())
children = fork(parent, n=3)
execute(children, edits)
out = evaluate(children, test)
best = select(out)
\end{lstlisting}
\end{columns}

\qadetail{The snippets illustrate a proposed API surface, not an existing SDK or a claim that these exact signatures are implemented. Both operate on the same three-element edits list, equivalent prepared input state, the same test function and the same select function. On the left, each iteration prepares a new environment, applies one edit and collects a test result. On the right, checkpoint captures the required reached state, the reused work of the cache and fork steps; fork creates three private writable children, each a sandbox; execute applies one edit per child and evaluate invokes the same test in each child. Result records identify their child, exact artifact and evidence. select applies the same selection rule in both sketches; it is not an infallible verifier and not the built numerical reducer. No concurrency or speedup value is asserted. Ordinary Python can use process fork, worktrees or warm caches to avoid repeated preparation; the interface adds no computational expressive power. The explicit API makes captured state and private continuations first-class orchestration objects; useful-state validity, code reload/restart, external effects, private writes and controller authority require their declared semantics.}
\note{[0:45] Both columns are Python, with the same three edits, the same test and the same selection rule. The loop prepares a fresh environment for every edit. The proposed API prepares once and checkpoints that state; fork makes three children, each a private sandbox; each applies one edit and returns its result with evidence. prepare() is the work we stop doing three times. Ordinary Python can already do this with process forks or caches; the API makes reuse and isolation explicit. None of these pieces is new on its own.}
