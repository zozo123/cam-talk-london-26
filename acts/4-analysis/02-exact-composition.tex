\begin{frame}[t]{Code changes that pass in pairs can fail when all three are merged.\ev{\tagA}}
\lead{Example: each change starts a \textbf{1 GB worker}. The server has \textbf{2 GB}.}
\begin{center}
{\fontsize{13}{16}\selectfont
\begin{tabular}{@{}lcc@{}}\toprule
\textbf{Merged changes} & \textbf{Memory used} & \textbf{Fits?}\\\midrule
A, B or C alone & 1 GB & \yes\ yes\\[5pt]
A+B, A+C or B+C & 2 GB & \yes\ yes\\[5pt]
A+B+C & 3 GB & \no\ no\\\bottomrule
\end{tabular}}
\end{center}
\claim{Run the checks on the final merged code before publishing it.}
\sources{Illustrative resource-capacity example; successful pair tests do not cover every larger combination.}

\qadetail{The example is illustrative and exact, not a recorded software incident. For fixed objective U, Gamma_ij=U({i,j})-U({i})-U({j})+U(empty). With U=1 for pass, the example gives zero pair interactions and a failing triple. Numerical reduction does not solve patch composition. The biological context is synthetic lethality: Gilad et al. screened knockouts lethal with an SRC-3 inhibitor; this is an analogy, not runtime data. Deterministic composition must preserve conflicts and resulting bytes before verification.}
\note{[0:45] Imagine three code changes. A starts one worker, B starts another and C starts a third. Each worker needs one gigabyte of memory, and the server has two gigabytes. Every change alone fits. Every pair fits. Merge all three and the program needs three gigabytes, so the combined configuration fails. Nothing in the successful pair tests covered that final state. The practical rule is straightforward: test the exact merged code you plan to publish. This example concerns interacting changes; the next one concerns overlapping information.}
\end{frame}
