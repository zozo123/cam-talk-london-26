\begin{frame}[t]{Choosing a result, merging code and pooling measurements are different operations.}
\begin{center}
{\fontsize{12.5}{16}\selectfont

\toprule\textbf{Operation} & \textbf{Example} & \textbf{What is checked?}\\\midrule
\textbf{Select} & Pick one of three model variants & The chosen model on evaluation data\\[6pt]
\textbf{Compose} & Merge two code changes & The actual merged code\\[6pt]
\textbf{Pool} & Combine estimates of one effect & Noise and information they share\\\bottomrule

\end{center}
\claim{The output determines the merge rule.}
\sources{Factory artifact checks and the numerical reducer illustrate different return paths.}

\qadetail{Three result lanes describe decision semantics, not three implemented end-to-end systems. Candidate selection needs a separately evaluated selector and cost/error model. Common-parameter pooling cannot combine different artifacts simply because each returns a number. Composition can create higher-order interactions. Fresh evaluation for generalization is different from a deterministic regression check, which can still establish its asserted behavior.}
\note{[0:45] Three branches can return three different kinds of output. If they trained different models, we might select the best candidate and evaluate that model. If they edited compatible parts of a program, we might compose the edits and test the merged code. If they estimated the same effect, we can pool measurements using their noise and dependence. Set union is useful for collecting distinct observations. Statistical pooling then asks how much those observations tell us about the target. A single universal merge cannot answer all these questions.}
\end{frame}
