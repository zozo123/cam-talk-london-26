{\small \tagP\ Share warm state on purpose, a build cache within one trust domain (risk: timing and content leaks)\quad$\cdot$\quad dependency image by digest (risk: a poisoned base)\quad$\cdot$\quad scratch never (risk: cross-branch contamination)\par}
\claim{Pick the kernel surface for the workload. Hand over authority explicitly.}
\sources{\href{https://github.com/MoonshotAI/Kimi-K3}{Kimi K3} \S5.3.2; Firecracker production host setup guide; Watson et al., Capsicum (USENIX Sec'10) and CHERI (IEEE S\&P'15).}
\note{[0:55] The child needs isolation along two axes, and this laboratory built systems for both. A container shares one kernel, gVisor moves it to user space, and a microVM stands on a hypervisor. An ordinary process can name whatever its user can name. Under Capsicum or CHERI, it can use only what it is handed. A build cache may be shared within one trust domain, meaning code trusted equally. Never share scratch. Kimi saw kernel panics in early container runtimes. Firecracker says disable SMT and same-page merging.}
