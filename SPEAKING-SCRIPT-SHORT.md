## 1 · Motivation  (0:00–8:35)

### 01 · Forkable sandboxes let computers explore alternatives without doing work twice.

*0:35 · starts 0:00*

> My path runs from self-organization in cells, to self-driving cars, to self-driving compute.  
> Once we have paid to reach a useful state, can we try several next steps from there without paying for it again?  
> My answer has three rules: compute once, count once, publish once.  
> The corner tags mark what is published, measured, built or only designed.  
> First, where these ideas come from.  

### 02 · Each stop on my path left one lesson.

*0:55 · starts 0:35*

> Here is my path, and each stop left one lesson.  
> In early systems jobs, including Twistlock, I worked on software and container security: a sandbox bounds what a program may do.  
> From twenty sixteen I simulated cell mechanics and analyzed genomes, where reaching a state is the expensive part, so you explore from there.  
> Our twenty nineteen study tested drug combinations on cancer cells: many trials, few confirmations.  
> At NRGene, editing results helped pick the next test.  
> At Mobileye, repeated observations of one road had to count once.  
> And at Incredibuild, the rule is simple: never build the same thing twice.  
> These lessons come back later, starting with Mobileye.  

### 03 · A car fleet fans out, then fans in to one map.

*0:45 · starts 1:30*

> Mobileye's Roadbook is a fleet example.  
> Assume three hundred million equipped cars sending anonymized road data.  
> The cloud matches drives of the same road, combines them, and sends the updated map back to the cars.  
> My own work there was junction perception.  
> Notice that the map counts each road once, however many cars drove it: count once.  
> Self-driving compute gives execution the same shape: many runs from one reached state, one combined result.  
> But a fleet of runs keeps doing the same work.  
> That is the problem.  

### 04 · In parallel computing, the costly work is the work done twice.

*0:55 · starts 2:15*

> Here is that problem in one picture.  
> `[ASK]` A question for you: how much of your last CI run was work another machine had already done? `[PAUSE]`  
> Often it is the same install and the same compile, again.  
> Without reuse, three trials each repeat the same setup.  
> `[CLICK]` With reuse, we set up once, save that state, and start every trial from it.  
> The setup blocks we skip are the waste: N minus one setups.  
> In a parallel, distributed world, the expensive thing is doing work twice. `[PAUSE]`  
> Three steps remove it: cache, fork, sandbox.  
> **Step one** is the oldest: a cache.  

### 05 · A cache skips work a previous run already did.

*0:45 · starts 3:10*

> Here is how a cache works.  
> Hash a build step's inputs, the source, the flags and the toolchain, into a key.  
> If the key is stored, that is a hit: reuse the stored output.  
> On a miss, run the step in a sandbox and store its output, so the next run hits.  
> The sandbox hides undeclared files, so the step cannot read what the key omits.  
> This is the Incredibuild lesson: never build the same thing twice.  
> Remember that hash; it comes back.  
> Here is what it buys.  

### 06 · Reusing an earlier runner's build files cut a Tokio compile from about 46 s to 13 s.

*0:40 · starts 3:55*

> In my Tokio demo, a fresh compile took about forty-six seconds.  
> Copying in an earlier runner's build files cut that to about thirteen, and an already warm cache to about three.  
> These times are approximate and author-reported, and the copied files are build outputs, not a running program.  
> Distributed builds rely on this: one machine reuses another's output.  
> A cache reuses one step's output.  
> **Step two** reuses a whole state.  

### 07 · A fork extends caching from files to a reached execution state.

*0:45 · starts 4:35*

> A fork goes further: it restores the state after many steps, such as installed dependencies or a warmed process.  
> Think of a film: fixed scenes, and rewinding replays the same plot.  
> An experiment saves a reached state, keyed by its digest like a cache entry, and tries two next actions, each in its own private sandbox.  
> A check keeps one outcome and discards the other, and we continue from there.  
> **Step three** makes that sharing safe.  

### 08 · A sandbox lets children share one state safely.

*0:50 · starts 5:20*

> Here is the sandbox.  
> In our design, three children share one saved state, read-only and named by its digest.  
> Each child writes only to its own private layer, so siblings cannot overwrite each other.  
> Undeclared inputs stay hidden, which keeps the cache key complete.  
> Effects, like a network request, do cross the boundary; no restore rewinds them, so we propose recording them.  
> This is the Twistlock lesson: a sandbox bounds behavior.  
> It is a policy; a VM with its own kernel, or a container sharing one, is one way to build it.  
> Here are the three steps as code.  

### 09 · The forkable API prepares once and runs alternatives in private children.

*0:45 · starts 6:10*

> Both columns are Python, with the same three edits, the same test and the same selection rule.  
> The loop prepares a fresh environment for every edit.  
> The proposed API prepares once and checkpoints that state; fork makes three children, each a private sandbox; each applies one edit and returns its result with evidence. prepare() is the work we stop doing three times.  
> Ordinary Python can already do this with process forks or caches; the API makes reuse and isolation explicit.  
> None of these pieces is new on its own.  

### 10 · Caches, forks and sandboxes are old; coupling them to evidence and acceptance is new.

*0:50 · starts 6:55*

> A cache keeps run outputs, as in ccache, Bazel's remote cache or Incredibuild.  
> A fork keeps reached states: SnowFlock cloned Xen machines in two thousand nine, and Xen came from this lab.  
> A sandbox keeps writes private, as containers, gVisor and microVMs do.  
> What is new is what sharing requires: count shared evidence once, and publish checked bytes once.  
> I do not claim a fork speedup, since our agent runs were serial, or that our snapshots keep live memory.  
> So what does sharing work cost us?  
> Three rules.  

### 11 · Sharing work creates three rules.

*0:50 · starts 7:45*

> Sharing work creates three obligations, and they organize this talk.  
> **Compute once**: reuse or rebuild?  
> Reuse a state only when that beats rebuilding it, even from a warm cache.  
> The answer is a cost rule.  
> `[CLICK]` **Count once**: what must a trial return?  
> Parallel trials share inputs and errors, so a shared observation counts once.  
> That needs an evidence contract.  
> `[CLICK]` **Publish once**: who publishes what?  
> One controller publishes the exact bytes that passed the check, through an acceptance gate.  
> You will leave with all three.  
> Five examples first, then the rules in order.

## 2 · Examples  (8:35–14:20)

### 12 · Reuse makes fuzzing fast; only checks turn crashes into findings.

*1:00 · starts 8:35*

> First example: software security.  
> A fuzzer runs a program on many changed inputs, hunting for crashes.  
> AFL-plus-plus initializes the target once, then reuses one child process across many inputs.  
> Its documentation reports typical speedups of ten to twenty times.  
> It wins by not forking for every input, as long as state resets correctly.  
> That is rule one, compute once.  
> But speed only produces leads, and leads need checks.  
> In a separate study, Berkeley's CyberGym, an AI agent wrote and ran inputs against 431 projects and produced fifty-six crashes.  
> The researchers reproduced them and removed duplicates: twenty-two distinct new vulnerabilities.  
> That is rule two, count once.  
> Second example: AI research.  

### 13 · Autoresearch kept 23 of 126 attempts against a fixed evaluator.

*1:00 · starts 9:35*

> Here, Karpathy's autoresearch starts every attempt from the incumbent commit, and the commit hash names that exact state.  
> The evaluator stays fixed.  
> The agent edits the training script, trains for five minutes, and reads validation bits per byte, where lower is better.  
> Then it keeps or reverts.  
> One reported session made 126 attempts, one at a time, and kept twenty-three.  
> The score fell 2.8 percent.  
> Starting from the incumbent is compute once; only the fixed evaluator promotes a change, which is publish once.  
> AlphaEvolve extends this loop to a population of programs; one scheduling heuristic it found recovered 0.7 percent of Google's compute, on average.  
> Third example: software engineering.  

### 14 · 250 samples raised SWE-bench Lite coverage from 15.9% to 56%.

> With one sample, a correct patch appeared for 15.9 percent of tasks.  
> With 250 samples, for 56 percent.  
> That is coverage: at least one patch passes the hidden tests.  
> In production there are no hidden tests.  
> A selector must pick one patch from many wrong ones, and only that patch ships.  
> Coverage is not selection.  
> That is rule three, publish once.

## 3 · Runtime: compute once  (14:20–17:45)

### 18 · The next step decides which state to reuse.

*1:05 · starts 14:20*

> To compute once, first ask what the reused state must hold.  
> That depends on the next step.  
> If it edits code and rebuilds, the cache we saw earlier supplies the files.  
> If it continues a live run, we restore a process or VM checkpoint and get only the memory that mechanism keeps.  
> If it needs an earlier answer, replay returns the recording.  
> What runs today is restore fan-out on islo, our sandbox service: many restores of one named snapshot.  
> Two hundred fifty-five of two hundred fifty-six restore-run-capture calls succeeded.  
> Whether live memory survives is untested until Gate zero, our first preregistered probe.  
> So pick the cheapest mechanism that supplies what the next step reads.  
> For a step that only reads files, a restore and a warm cache compete.  

### 19 · A restore pays only if it beats a warm cache.

*1:15 · starts 15:25*

> Here is the rule.  
> With N alternative runs, each would repeat a setup cost, P; preparing once avoids N minus one copies.  
> Against that we pay H to save the state once, and per child, R to restart it and D to keep its writes private.  
> Sandbox starts are already cheap, as low as seventy-three milliseconds in a public benchmark, so P must be real preparation.  
> `[ASK]` A question for you: restore a snapshot, or rebuild with a warm cache: which wins? `[PAUSE]`  
> `[CLICK]` Take eight runs, H of two, R of one, D of three: thirty-four resource-seconds of overhead.  
> With a cold setup of thirty, restoring avoids two hundred ten and saves a hundred seventy-six.  
> `[CLICK]` With a warm cache, setup drops to two: restoring avoids only fourteen and costs twenty more.  
> The warm cache wins: never build the same thing twice. `[PAUSE]`  
> But even a winning restore cannot undo everything.  

### 20 · A restore cannot undo remote effects, and a fork must not hold the right to publish.

*1:05 · starts 16:40*

> First, remote effects.  
> Save a sandbox, call a hosted model, then restore.  
> The sandbox is back, but the model has already answered and charged us.  
> A restore cannot rewind another service, so an effect is not computed once; it is recorded once, outside the child.  
> Our proposed design retries with an idempotency key that the controller mints for each child, so a fork never copies it.  
> Second, recall the Twistlock lesson: a sandbox is a policy boundary.  
> A fork copies every credential inside it, so the right to publish must never be inside.  
> The worker returns a patch and its test records; only the controller holds the publish key.  
> Our factory runs exercised that separation.  
> **Rule two**: count once.

## 4 · Evidence: count once  (17:45–22:25)

### 21 · A receipt is evidence's cache entry, written outside the child.

*1:05 · starts 17:45*

> Counting once starts with a record of what each trial did: a receipt.  
> It works like a cache entry.  
> The key is what ran, on which bytes, from which inputs; a hash names the bytes, as in the cache.  
> The value is the result and who reported it.  
> In our design the harness writes it, outside the child; a child's own report is only a claim.  
> Our factory logs show why.  
> A CI job passed in three seconds; its evaluation had been skipped.  
> A helper's code hash was recorded, but its source was not in the repository: a hash is a fingerprint, not a backup.  
> An approval was labelled human; the harness had answered it.  
> The inputs field lets a shared observation count once.  
> Next, we combine receipts.  

### 22 · Each fan-in operation needs its own check.

*1:00 · starts 18:50*

> Combining receipts is called fan-in, and it is not one operation.  
> If the trials tried different ideas, we select one, like the patch selector in the software example.  
> Selection is itself a search, so we recheck the winner on fresh data.  
> If the trials edited different parts of a program, we compose their edits, and the merged version needs its own test.  
> A made-up example: each change starts a one-gigabyte worker on a two-gigabyte server.  
> Each change fits.  
> Every pair fits.  
> All three fail, and no pair test covered that.  
> If the trials estimated one quantity, we pool them, and the weights must account for errors they share.  
> So first: what do trials share?  

### 23 · Overlapping trials add less than their count.

*0:50 · starts 19:50*

> The simplest thing trials share is an observation.  
> Trial A returns a, b and c; trial B returns b, c and d.  
> That is four distinct observations, not six, so B adds only d.  
> We have seen this before.  
> The Roadbook counts a road once, however many drives cross it.  
> Six guides aimed at one gene are six looks at one gene.  
> Today, our reducer rejects a duplicate observation ID and keeps each result's source history.  
> But different observations can still share errors.  

### 24 · At error correlation 0.1, a mean of 100 estimates is as precise as about nine.

*0:50 · starts 20:40*

> Take a hundred equally noisy estimates whose errors have pairwise correlation point one.  
> They might share a parent state, a seed or a test fixture.  
> Their average reduces noise only as much as about nine independent estimates, not a hundred.  
> Shared errors count for less, and a shared bias does not average away at all.  
> Our reducer still assumes independence.  
> Proposed: weights that use the error covariance, and refusing a precision claim when the dependence is unknown.  
> Worse than a shared error is a worker that overstates its own precision.  

### 25 · A worker that overstates its precision can take over the average.

*0:55 · starts 21:30*

> A weighted average multiplies each estimate by its precision, one over its variance, so a worker that claims little uncertainty gets a large weight.  
> In our synthetic test the true value is five.  
> One worker sends two thousand tight points near seventeen and inflates its information per point fiftyfold.  
> Counting points would not catch it.  
> Trusting reported precision, the average is seventeen point zero zero zero four: one worker took over.  
> `[CLICK]` Our heuristic caps that precision and down-weights far-off estimates: four point nine five six six.  
> One synthetic case, not a Byzantine guarantee.  
> So check outside the child, including its error bars.  
> **Rule three**: publish once.

## 5 · Acceptance: publish once  (22:25–25:40)

### 26 · Our factory's patch passed every check it had.

*0:55 · starts 22:25*

> Our own factory run shows why.  
> It was serial, on Docker sandboxes; nothing forked.

> The promise: the job starts once.  
> No test forces that path.  
> `[CLICK]` Review approved, suite green, promise untested. `[PAUSE]`  
> I reverted that path by hand; the PR merged on 3 October without it.  
> A person caught what the gate should catch. `[PAUSE]`  
> What should that gate be?  

### 27 · Accept only bytes whose promise was tested.

*0:50 · starts 23:20*

> Three steps.  
> First, freeze the candidate and its hash.  
> The hash that keyed the cache now names the bytes the controller may publish; it proves identity, not correctness.  
> Second, require a test for each promise the change makes, and run it on those exact files.  
> Here: force the retry onto a busy workspace and assert one dispatch.  
> Third, the controller publishes only that hash.  
> That hash-bound publish check is built; the promise test is proposed.  
> No test for the promise, no acceptance: this gate would have refused our patch. `[PAUSE]`  
> A checked result also has to survive.  

### 28 · Our second factory run lost an approved patch.

*0:45 · starts 24:10*

> In a second factory run, review approved a patch, but delivery was refused three times over a stray file: the harness's own review archive.  
> Then cleanup deleted the workspace, and the approved patch with it.  
> The fix is an order: save a copy outside the child, confirm the copy, then delete.  
> A hash alone is not a copy.  
> The order is proposed; the loss was real.  
> But saving is not permission to publish: a replaced or restored worker may still try to deliver.  

### 29 · The controller rejects a late result from a replaced worker.

*0:45 · starts 24:55*

> So the controller keeps an epoch, a permission version number.  
> Replacing a worker moves the epoch from one to two.  
> A late result from the old worker still carries one, so the controller rejects it.  
> The check lives in the controller, so restoring a snapshot cannot revive an old permission.  
> And a publish keyed by the digest makes a retry a no-op, like a cache hit.  
> Both are proposed.  
> One controller, current epoch, publish once.

## 7 · Conclusion  (26:45–27:45)

### 31 · Contributions: three rules for doing work once.

*1:00 · starts 26:45*

> My contributions, on the same map we started with.  
> **Compute once**: a cost rule.  
> Restore saved state only when the setup it avoids exceeds the overhead it adds, priced against a warm cache.

> **Compute once**.  
> **Count once**.  
> **Publish once**.
