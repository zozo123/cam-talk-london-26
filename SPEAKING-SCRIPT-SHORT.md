### 05 · A cache skips work a previous run already did.

*0:45 · starts 3:10*

> Here is how a cache works.  
> Hash a build step's inputs into a key: source, flags and toolchain.  
> If the key is stored, that is a hit.  
> Reuse the stored output.  
> On a miss, run the step in a sandbox.  
> Store its output, so the next run hits.  
> The sandbox hides undeclared files, so the step cannot read what the key omits.  
> This is the Incredibuild lesson: never build the same thing twice.  
> Remember that hash, because it comes back.  
> What does it buy?  

### 06 · Reusing an earlier runner's build files cut a Tokio compile from about 46 s to 13 s.

*0:40 · starts 3:55*

> In my Tokio demo, a fresh compile took about forty-six seconds.  
> Copying in an earlier runner's build files cut that to about thirteen.  
> An already warm cache cut it to about three.  
> These are approximate, self-reported times.  
> The copied files are build outputs, not a running program.  
> Distributed builds rely on this: one machine reuses another's output.  
> A cache reuses one step's output.  
> **Step two** reuses a whole state.  

### 07 · A fork extends caching from files to a reached execution state.

*0:45 · starts 4:35*

> A fork goes further.  
> It restores the state after many steps, like installed dependencies or a warmed process.  
> Think of a film.  
> Its scenes are fixed, and rewinding replays the same plot.  
> An experiment is different.  
> It saves a reached state, keyed by its hash, like a cache entry.  
> It tries two next actions, each in its own private sandbox.  
> A check keeps one outcome and discards the other.  
> Then we continue from there.  
> **Step three** makes that sharing safe.  

### 08 · A sandbox lets children share one state safely.

*0:50 · starts 5:20*

> In our design, three children share one saved state.  
> It is read-only and named by its hash.  
> Each child writes only to its private layer, so siblings cannot overwrite each other.  
> Hiding undeclared inputs keeps the cache key complete.  
> Effects, like a network request, cross the boundary.  
> No restore rewinds them, so we propose recording them.  
> This is the Twistlock lesson: a sandbox bounds what a program may do.  
> It is a policy.  
> One way to build it is a VM with its own kernel.  
> Another is a container on a shared kernel.  
> Here are the three steps as code.  

### 09 · The forkable API prepares once and runs alternatives in private children.

*0:45 · starts 6:10*

### 10 · Caches, forks and sandboxes are old; coupling them to evidence and acceptance is new.

*0:50 · starts 6:55*

## 3 · Runtime: compute once  (14:40–18:05)

### 18 · The next step decides which state to reuse.

*1:05 · starts 14:40*

> What must the reused state hold?  
> The next step decides.  
> If it edits code and rebuilds, the cache from earlier supplies the files.  
> If it continues a live run, we restore a process or VM checkpoint.  
> We get only the memory that mechanism keeps.  
> If it needs an earlier answer, replay returns the recording.  
> Today we run restore fan-out on islo, our sandbox service.  
> That means many restores of one named snapshot.  
> Two hundred fifty-five of two hundred fifty-six restore-run-capture calls succeeded.  
> Whether live memory survives is untested until Gate zero, our first preregistered probe.  
> So pick the cheapest mechanism that supplies what the next step reads.  
> For a step that only reads files, a restore and a warm cache compete.  

### 19 · A restore pays only if it beats a warm cache.

*1:15 · starts 15:45*

> Here is the rule.  
> With N alternative runs, each would repeat a setup cost, P.  
> Preparing once avoids N minus one setups.  
> Against that, we pay H to save the state once.  
> Each child pays R to restart and D to keep its writes private.  
> Sandbox starts are already cheap.  
> A public benchmark puts them as low as seventy-three milliseconds.  
> So P must be real preparation.  
> `[ASK]` A question for you: which wins, a snapshot restore or a warm-cache rebuild? `[PAUSE]`  
> `[CLICK]` Take eight runs, H of two, R of one, D of three.  
> That is thirty-four resource-seconds of overhead.  
> With a cold setup of thirty, restoring avoids two hundred ten.  
> So it saves a hundred seventy-six.  
> `[CLICK]` With a warm cache, setup drops to two.  
> Restoring avoids only fourteen, so it loses twenty.  
> The warm cache wins: never build the same thing twice. `[PAUSE]`  
> But even a winning restore cannot undo everything.  

### 20 · A restore cannot undo remote effects, and a fork must not hold the right to publish.

*1:05 · starts 17:00*

> First, remote effects.  
> Save a sandbox, call a hosted model, then restore.  
> The sandbox is back, but the model has already answered and charged us.  
> A restore cannot rewind another service.  
> So an effect is not computed once, but recorded once, outside the child.  
> Our proposed design retries with an idempotency key.  
> The controller gives each child its own key, so forks never share one.  
> Second, credentials.  
> A fork copies every credential inside the sandbox.  
> So the publish key must stay outside.  
> The worker returns a patch and its test records.  
> Only the controller holds that key.  
> Our factory runs exercised that separation.  
> **Rule two**: count once.

## 4 · Evidence: count once  (18:05–22:45)

### 21 · A receipt is evidence's cache entry, written outside the child.

*1:05 · starts 18:05*

> Counting once starts with a receipt.  
> A receipt records what each trial did.  
> It works like a cache entry.  
> The key is what ran, on which bytes, from which inputs.  
> A hash names the bytes, as in the cache.  
> The value is the result and who reported it.  
> In our design, the harness writes it, outside the child.  
> A child's own report is only a claim.  
> Our factory logs show why.  
> A CI job passed in three seconds, but its evaluation was skipped.  
> A helper's code hash was recorded, but its source was not in the repository.  
> A hash is a fingerprint, not a backup.  
> An approval was labelled human, but the harness had answered it.  
> The inputs field lets a shared observation count once.  
> Next, we combine receipts.  

### 22 · Each fan-in operation needs its own check.

*1:00 · starts 19:10*

> Combining receipts is called fan-in, and it is not one operation.  
> If the trials tried different ideas, we select one.  
> Recall the patch selector in the software example.  
> Selection is itself a search.  
> So we recheck the winner on fresh data.  
> If the trials edited different parts of a program, we compose their edits.  
> The merged version needs its own test.  
> A made-up example: each change starts a one-gigabyte worker on a two-gigabyte server.  
> Each change fits.  
> Every pair fits.  
> All three together fail, and no pair test catches that.  
> If the trials estimated one quantity, we pool them.  
> The weights must account for errors they share.  
> So first, what do trials share?  

### 23 · Overlapping trials add less than their count.

*0:50 · starts 20:10*

> The simplest thing trials share is an observation.  
> Trial A returns a, b and c.  
> Trial B returns b, c and d.  
> That is four distinct observations, not six, so B adds only d.  
> We have seen this before.  
> The Roadbook counts a road once, however many drives cross it.  
> Six guides aimed at one gene are six looks at one gene.  
> Our reducer pools the results.  
> Today, it rejects a duplicate observation ID.  
> It also keeps each result's source history.  
> But different observations can still share errors.  

### 24 · At error correlation 0.1, a mean of 100 estimates is as precise as about nine.

*0:50 · starts 21:00*

> Take a hundred equally noisy estimates.  
> Their errors have pairwise correlation point one.  
> They might share a parent state, a seed or a test fixture.  
> Their average is as precise as about nine independent ones, not a hundred.  
> Shared errors count for less.  
> A shared bias does not average away at all.  
> Our reducer still assumes independence.  
> We propose weights that use the error covariance.  
> We also propose refusing a precision claim when the dependence is unknown.  
> A worker that overstates its own precision is worse than a shared error.  

### 25 · A worker that overstates its precision can take over the average.

*0:55 · starts 21:50*

> A weighted average multiplies each estimate by its precision, one over its variance.  
> So a worker claiming little uncertainty gets a large weight.  
> In our synthetic test, the true value is five.  
> One worker sends two thousand tight points near seventeen.  
> It claims fifty times its real precision.  
> Counting points would not catch it.  
> If we trust that precision, the average is seventeen point zero zero zero four.  
> One worker took over.  
> `[CLICK]` Our heuristic caps that precision and down-weights far-off estimates.  
> That gives four point nine five six six.  
> One synthetic case, not a Byzantine guarantee.  
> So check outside the child, including its error bars.  
> **Rule three**: publish once.

### 27 · Accept only bytes whose promise was tested.

*0:50 · starts 23:40*

> Three steps.  
> First, freeze the candidate and its hash.  
> The hash that keyed the cache now names the bytes the controller may publish.  
> It proves identity, not correctness.  
> Second, require a test for each promise the change makes.  
> Run it on those exact files.  
> Here, force the retry onto a busy workspace and assert one dispatch.  
> Third, the controller publishes only those bytes.  
> That hash-bound publish check is built, but the promise test is proposed.  
> No test for the promise, no acceptance: this gate would have refused our patch. `[PAUSE]`  
> A checked result also has to survive.  

### 28 · Our second factory run lost an approved patch.

*0:45 · starts 24:30*

> In a second factory run, review approved a patch.  
> But delivery was refused three times, over a stray file.  
> That file was the harness's own review archive.  
> Then cleanup deleted the workspace, and the approved patch with it.  
> The fix is an order.  
> Save a copy outside the child, confirm the copy, then delete.  
> A hash alone is not a copy.  
> The order is proposed.  
> The loss was real.  
> But saving is not permission to publish.  
> A replaced or restored worker may still try to deliver.  

### 29 · The controller rejects a late result from a replaced worker.

*0:45 · starts 25:15*

> So the controller keeps an epoch, a permission version number.  
> Replacing a worker moves the epoch from one to two.  
> The old worker's late result still carries one, so the controller rejects it.  
> The check lives in the controller.  
> That way, restoring a snapshot cannot revive an old permission.  
> We also key each publish by its hash.  
> Then a retry is a no-op, like a cache hit.  
> Both are proposed.  
> One controller, current epoch, publish once.
